# 와플스튜디오 세미나 운영 관리 서비스 Waggle

2주차부터 4주차까지 조별로 완성할 서비스의 전체 요구사항입니다. 5주차에는 이 서비스를 배포합니다.

이 Waggle 서비스가 **무엇을 해야 하는지**를 설명합니다. 각 주차에 구현할 엔드포인트와 요청·응답 형식은 주차별 과제 문서에서 공개합니다.

> **이 문서와 주차별 과제 안내에 적혀 있지 않은 사항은 자유롭게 구현해도 됩니다.** 공개 테스트는 여기에 적힌 동작과 주차별 과제 문서의 API 명세만 확인합니다.

> 누가 어떤 기능을 쓸 수 있는지에 대한 자세한 설명은 3주차(인증 인가) 때 제시할 예정입니다.

---

## 1. 서비스 소개
백문이 불여일견. 데모페이지를 확인해주세요. (링크)

와플스튜디오에는 Frontend, Spring, FastAPI 등 여러 세미나가 있습니다. 이 서비스는 그 세미나들의 수강 신청과 수업 운영을 처리합니다.

`루키`는 서비스에 가입해 원하는 세미나에 **선착순으로 수강 신청**하고, `운영진`은 자신이 담당하는 세미나의 수업 회차를 열고 **루키들의 출석과 과제 제출 현황을 관리**합니다. 즉 Waggle은 루키를 위한 세미나 신청 기능과 운영진/와장을 위한 세미나 관리 기능을 동시에 제공합니다.


- **루키**는 서비스에 가입한 뒤 세미나에 선착순으로 신청하고, 수업과 과제 안내를 확인하며 자신의 출석과 과제 현황을 봅니다.
- **운영진**은 담당 세미나의 수업 회차를 등록하고, 수업·과제 안내를 작성하고, 수강생의 출석과 과제 현황을 관리합니다.
- **와장**은 운영진과 루키의 서비스 가입을 심사하고 세미나를 개설합니다.

모든 조는 과제 운영진이 제공하는 **같은 API 명세**를 구현합니다. 내부 구조와 설계는 조마다 자유롭게 결정합니다.

## 2. 역할 핵심 설명

| 역할 | 설명 |
| --- | --- |
| 와장 (`ADMIN`) | 서비스 전체를 관리합니다. 가입으로 생성되지 않고 처음부터 DB에 존재합니다. |
| 운영진 (`STAFF`) | 세미나 하나를 담당하며 그 세미나를 운영합니다. |
| 루키 (`ROOKIE`) | 세미나를 수강하는 사용자입니다. |

- 한 사용자는 하나의 역할(와장, 운영진, 루키)만 가집니다. 예를 들어 운영진이면서 루키일 수 없습니다.
- 역할은 가입할 때 정해지며 이후 바뀌지 않습니다.
- 운영진은 **정확히 하나의 세미나**를 담당합니다. 한 세미나에는 여러 명의 운영진이 있을 수 있습니다.
- 루키는 여러 세미나를 들을 수 있습니다.

## 3. 기능 요구사항

### 3.1 가입과 가입 심사

유저는 이메일, 비밀번호, 이름, GitHub 사용자명을 입력해 운영진 또는 루키로 Waggle에 가입신청을 합니다. 운영진으로 가입 신청을 할 때는 담당할 세미나 하나를 함께 고릅니다. 가입으로 와장이 될 수는 없습니다.

가입했다고 바로 서비스를 쓸 수 있는 것은 아닙니다. 가입 신청은 **대기** 상태로 남아 있다가 심사를 거쳐 **승인**되거나 **반려**됩니다.

```
PENDING ──승인──> APPROVED
   │
   └────반려──> REJECTED
```

심사는 운영진과 와장이 합니다. 대기 또는 반려 상태의 사용자는 로그인할 수 있지만, 서비스를 이용할 수는 없고 안내 페이지만을 보게 됩니다. 
- 운영진 가입 신청은 와장이 심사합니다.
- 루키 가입 신청은 운영진 또는 와장이 심사합니다.

### 3.2 세미나

세미나는 와장만이 개설할 수 있습니다. 세미나에는 제목과 설명, 정원, 수강 신청을 받는 기간, 그리고 수강생에게 줄 총 Grace Day 수가 있습니다.

| 항목 | 설명 |
| --- | --- |
| 제목 | 필수 |
| 설명 | 세미나 소개 글 |
| 정원 | 신청할 수 있는 최대 인원. |
| 신청 시작 일시 · 신청 종료 일시 | 수강 신청을 받는 기간 |
| 총 Grace Day | 수강생마다 이 값에서 시작합니다. |

세미나는 항상 신청 가능한 것이 아닙니다. 현재 시각과 신청 시작/종료 일시, 그리고 정원 마감 여부에 따라 달라집니다. 루키는 `신청 중` 인 세미나만 신청 가능합니다. 

| 상태 | 조건 |
| --- | --- |
| 신청 전 | 현재 < 신청 시작 시각 |
| 신청 마감 | 신청 종료 시각 ≤ 현재 or `정원 도달`|
| 신청 중 | 신청 기간 내이며 정원이 마감되지 않음 (신청 전 또는 신청 마감이 아닌 것) |

유저가 세미나를 조회할 때에는 세미나 생성 시에 결정한 정원과 함께, **현재 몇 명이 신청했는지**도 볼 수 있습니다. 선착순 신청이라 남은 자리가 중요합니다.

개설한 세미나는 삭제가 불가능합니다. 세미나에서 수정 가능한 것은 제목 또는 설명 뿐입니다.

### 3.3 수강 신청

루키는 신청 기간 안에 원하는 세미나를 신청합니다. **선착순**이므로 별도 승인 없이 즉시 확정되고, 정원이 이미 찼다면 신청할 수 없습니다.

한 루키가 신청할 수 있는 세미나 개수에는 제한이 없습니다. 마음이 바뀌면 **신청 기간 안에서** 취소할 수 있습니다. 취소하면 자리가 비고, 다른 루키가 그 자리에 신청할 수 있습니다. 신청 기간이 끝나면 신청도 취소도 할 수 없습니다.

신청이 확정되면 루키는 그 세미나에서의 수강 정보를 볼 수 있습니다.

| 항목 | 초기값 | 설명 |
| --- | --- | --- |
| 잔여 Grace Day | 세미나의 총 Grace Day | 운영진이 직접 조정합니다. |
| 탈락 여부 | 탈락 아님 | 운영진이 직접 표시합니다. |

또한 `회차별 출석`과 `과제` 현황도 이 수강 정보에 쌓입니다. 루키는 자신이 신청한 세미나 목록을 볼 수 있고, 세미나의 수강생 목록은 수가 많을 수 있으므로 페이지 단위로 조회할 수 있습니다.

### 3.4 수업 회차와 안내

한 세미나는 여러 회차의 수업으로 구성됩니다. 수업 일정은 세미나를 만들 때 미리 정해지지 않고, **운영진이 수업을 하기 전에 해당 회차를 하나씩 등록**합니다.

| 항목 | 설명 |
| --- | --- |
| 회차 번호 | 해당 세미나의 회차를 `startsAt` 오름차순으로 정렬했을 때의 1, 2, 3, …입니다. 같은 시각이면 회차 ID 오름차순으로 순서를 정합니다. 회차 번호는 저장하지 않고 이 순서에서 계산하는 표시용 값입니다. |
| 제목 | 그 회차 수업의 제목 |
| 시작 일시 · 장소 | 회차마다 다를 수 있습니다. |
| 과제 제목 | 회차마다 과제가 항상 하나 있습니다. |
| 수업 설명 · 과제 설명 | 선택. Markdown 텍스트 |

수업 회차는 날짜 순서와 관계없이 등록할 수 있습니다. 조회와 화면 표시에서는 `startsAt`, 같은 시각이면 회차 ID 오름차순으로 정렬합니다. 따라서 더 이른 시각의 회차를 나중에 등록하면 기존 회차의 표시 번호가 바뀔 수 있습니다.

운영진은 회차마다 **수업 설명과 과제 설명을 Markdown으로 작성**합니다. 나중에 고치거나 지울 수 있고, 그 세미나의 수강생이 읽습니다.

### 3.5 출석과 과제 기록

운영진은 회차마다 수강생 한 명 한 명의 출석 상태와 과제 제출 상태를 기록할 수 있습니다.

| 기록 | 상태 값 |
| --- | --- |
| 출석 | `PRESENT`(출석),  `ABSENT`(결석) |
| 과제 | `PASSED`(통과), `SUBMITTED_BUT_FAILED`(제출했으나 실패), `NOT_SUBMITTED`(미제출) |

아직 기록하지 않은 칸은 **빈칸**으로 남습니다. 결석이나 미제출로 간주하지 않습니다. 한 회차에서 한 수강생의 출석 기록과 과제 기록은 각각 하나씩만 존재하며, 다시 기록하면 기존 값을 바꿉니다.

Grace Day는 과제가 늦었을 때 쓰는 여유분입니다. 운영진이 상황을 보고 **남은 개수를 직접 조정**합니다. 0보다 작거나 세미나의 총 Grace Day보다 클 수는 없습니다. 탈락 여부도 운영진이 직접 표시하며, 표시용일 뿐 정원이나 기록 수정 등 다른 기능에는 영향을 주지 않습니다.

### 3.6 현황 조회 (대시보드)

운영진은 담당 세미나의 루키 현황을 표 대시보드로 편집합니다. **행은 수강생, 열은 회차**인 표입니다.

| 이름 | 이메일 | GitHub | 잔여 Grace Day | 탈락 여부 | 1회차 출석 | 1회차 과제 | 2회차 출석 | 2회차 과제 | … |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 김와플 | … | … | 2 | | 출석 | 통과 | 결석 | | … |

잔여 Grace Day, 탈락 여부, 회차별 출석과 과제 란을 운영진이 고칠 수 있습니다.

루키는 자신이 수강 중인 세미나의 표 대쉬보드를 조회할 수 있습니다. (다른 수강생의 정보도 볼 수 있습니다.) 대쉬보드를 편집할 수는 없습니다.

## 4. 2주차 스키마 설계 시 고려사항

2주차에는 이 요구사항을 바탕으로 서비스 전체의 ERD를 설계합니다. 아래 다섯 가지를 어떻게 표현할지 먼저 생각해 보세요.

- 한 `운영진`은 **오직 하나의 세미나**를 담당하지만, 한 `세미나`에는 **여러 운영진**이 있을 수 있습니다.
- 한 `루키`는 **여러 세미나**를 수강할 수 있고 한 세미나에는 **여러 명의 루키**가 있습니다.
- 잔여 Grace Day와 탈락 여부는 루키의 정보가 아니라 **"이 루키가 이 세미나를 수강하는 것"에 대한 정보**입니다. 따라서 같은 루키라도 세미나마다 값이 다릅니다.
- 출석과 과제 기록은 **어떤 수업 회차의, 어떤 루키 수강생에 대한** 기록입니다.
- 세미나를 조회할 때마다 필요한 **현재 신청 인원**을 어떻게 구할지도 함께 생각해 보세요.
