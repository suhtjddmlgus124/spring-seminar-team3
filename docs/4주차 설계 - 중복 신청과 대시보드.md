# 4주차 설계: 중복 신청 방지와 대시보드 (담당: 방우식)

팀 설계 문서의 한 절이다. 정원 경쟁·중복 취소·기록 일괄 수정 절은 각 담당이 덧붙인다.

## 1. 중복 신청

### 어떤 문제가 있었는가
한 루키가 같은 세미나에 동시에 신청하면 다음 순서가 가능하다.

```
요청 A: existsBySeminarIdAndRookieId → false
요청 B: existsBySeminarIdAndRookieId → false
요청 A: INSERT enrollments  → 성공
요청 B: INSERT enrollments  → UNIQUE(rookieId, seminarId) 위반
```

V1 부터 `UQ_enrollments_rookieId_seminarId` 가 있어서 행이 두 개 생기지는 않았다. 하지만 B 의 `DuplicateKeyException` 을 처리하지 않아 응답이 500 이었다.
재현: 수정 전 코드로 `team/DuplicateEnrollmentConcurrencyTest` 를 돌리면 "동시 요청 실행 중 예상하지 못한 예외"로 실패한다.

### 왜 발생했는가
조회(exists)와 저장(INSERT) 사이에 다른 요청이 끼어들 수 있다. 트랜잭션으로 묶어도 MySQL 기본 격리 수준(REPEATABLE READ)의 일반 SELECT 는 잠금을 걸지 않으므로, 두 트랜잭션이 모두 "없음"을 본다.

### 어떻게 해결했는가
- 최종 판단은 DB 의 UNIQUE 제약이 한다. 애플리케이션의 exists 검사는 순차 요청을 빠르게 거르는 용도로만 남겼다.
- `EnrollmentService.saveUnlessDuplicated` 에서 `DuplicateKeyException` 을 잡는다. 원인 메시지에 위 인덱스 이름이 있을 때만 `AlreadyEnrolledException`(409)으로 바꾸고, 다른 DB 오류는 그대로 던진다(예상하지 못한 오류를 409 로 숨기지 않는다).
- 실패한 INSERT 는 행을 남기지 않으므로 빈자리를 소비하지 않는다.

### 왜 이 방법인가
| 방법 | 판단 |
|---|---|
| UNIQUE 제약 + 위반 변환 (선택) | 이미 있는 제약을 쓰므로 스키마 변경이 없다. 대기·재시도가 없다. 중복은 "한 사람·한 세미나" 문제라 행 단위 제약이 정확히 맞는다 |
| 세미나 행 비관적 락 | 정원 경쟁에는 필요할 수 있지만, 중복만 막으려고 세미나 전체 신청을 직렬화하는 건 과하다 |
| 애플리케이션 락(synchronized 등) | 서버가 여러 대면 무력하다 |

정원 경쟁 담당이 세미나 행 락을 도입하면 중복 신청도 그 락 안에서 순차 처리된다. 그래도 UNIQUE 변환은 마지막 방어선으로 남겨 둔다.

### 트랜잭션 경계
신청은 INSERT 한 건이다. 위반 시 예외를 다시 던지므로, 바깥에 `@Transactional` 이 생겨도 그 트랜잭션은 롤백된다(`AlreadyEnrolledException` 은 `RuntimeException`).

### 검증
- 위치: `src/test/kotlin/com/wafflestudio/spring2026/team/DuplicateEnrollmentConcurrencyTest.kt`
- 실행: `colima start` 후 `./gradlew test --tests '*DuplicateEnrollmentConcurrencyTest'`
- 시나리오: 정원 3 세미나에 한 루키가 20회 동시 신청 → 201 1건, 409 19건, DB 의 그 루키 신청 1개. 이후 다른 루키 2명 성공, 1명 409 → 실패 19건이 자리를 쓰지 않았다.
- 공개 테스트 `EnrollmentConcurrencyApiTest` 의 "동일 사용자의 동시 신청" 통과.

## 2. 대시보드 `GET /seminars/{id}/dashboard`

- 회차는 `startsAt`, `id` 오름차순으로 읽고 `round` 는 그 순서의 1부터 매긴다(기존 회차 조회와 같은 기준).
- 수강생 행은 수강 신청 ID 오름차순, `LIMIT/OFFSET` 으로 이번 페이지만 읽는다. 기록은 이번 페이지 신청 ID 들의 것만 한 번에 읽어 `(enrollmentId, sessionId)` 로 붙인다. 기록이 없는 칸은 두 값 모두 `null`.
- 회차·수강생·기록 조회를 `@Transactional(readOnly = true)` 하나로 묶었다. REPEATABLE READ 스냅샷을 공유하므로 조회 도중 신청·취소가 있어도 `totalElements` 와 `content` 가 어긋나지 않는다.
- 권한: `AccessPolicy.requireDashboardViewer` (와장, 담당 운영진, 수강 중인 루키). 없는 세미나 404 를 먼저 본다.
- `Participation` 모델의 `rookieId` 를 DB 컬럼과 같은 `enrollmentId` 로 고쳤다(V1 스키마는 처음부터 `enrollmentId`).
