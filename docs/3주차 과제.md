## 1. 토큰 발급과 인증

로그인에 성공하면 서버는 JWT 형식의 Access Token 을 발급합니다. 이후 요청한 사람이 누구인지 확인해야 하는 요청에서는, 요청 헤더에 담긴 이 토큰을 검사해 요청자를 확인합니다. 이를 인증(Authentication)이라 하며, 요청자를 확인할 수 없으면(토큰이 없거나, 잘못됐거나, 만료됐거나, 로그아웃으로 무효화됨) `401` 을 반환합니다.

<a id="jwt"></a>
### JWT Access Token

JWT 는 `헤더.페이로드.서명` 세 부분을 `.` 으로 이은 문자열입니다. 페이로드에는 클레임(claim)이라 부르는 값들을 담고, 서명은 서버만 아는 키로 만듭니다. 서버는 서명을 확인해 토큰이 위조되지 않았음을, `exp` 를 확인해 만료되지 않았음을 판단합니다. 페이로드는 암호화가 아니라 인코딩일 뿐이라 누구나 읽을 수 있으므로, 비밀번호 같은 민감한 정보는 담지 않습니다.

이번 과제에서 발급하는 토큰은 아래 규칙을 따라야 합니다.

| 클레임 | 값 |
| --- | --- |
| `sub` | 사용자 ID (문자열. 예: `"7"`) |
| `iat` | 발급 시각 (초 단위 Unix 시각) |
| `exp` | 만료 시각. **발급 후 1시간**, 즉 `exp = iat + 3600` |

- 위 세 클레임은 필수입니다. 그 밖의 클레임은 자유롭게 추가해도 됩니다.
- 서명은 **HS256** 으로 하고, 서명 키는 `application.yaml` 의 **`jwt.secret`** 값(UTF-8 바이트)을 그대로 씁니다. 3주차 자료로 이 설정이 들어옵니다.
- 테스트는 `jwt.secret` 을 테스트용 값으로 바꿔 실행하고, 발급된 토큰의 클레임을 읽거나 같은 키로 만든 토큰(예: 이미 만료된 토큰)을 보내 확인합니다.
- `jwt.secret` 에 적힌 값은 개발용입니다. 공개 저장소라 누구나 볼 수 있으므로, 실제로 배포할 때는 환경 변수 `JWT_SECRET` 으로 덮어써야 합니다.

### 비밀번호 Hash 저장

비밀번호를 원문 그대로 저장하면 DB가 유출되었을 때 비밀번호도 함께 노출되므로 보안상 안전하지 않습니다. 따라서 [회원가입](#signup) 시 Spring Security 의 `PasswordEncoder` 로 만든 Hash 를 저장합니다. 로그인할 때는 입력받은 비밀번호와 저장된 Hash 가 일치하는지 `PasswordEncoder` 로 검증합니다.

<a id="login"></a>
### 로그인과 토큰 발급
로그인을 위한 엔드포인트를 새롭게 만듭니다.

`POST /auth/login` — 이메일과 비밀번호로 로그인하고 JWT 형식의 Access Token 을 받습니다.


**요청**

```json
{
  "email": "waffle@snu.ac.kr",
  "password": "********"
}
```

| 항목 | 타입 | 필수 | 제약 |
| --- | --- | --- | --- |
| `email` | string | ✓ | 공백 불가 |
| `password` | string | ✓ | 공백 불가 |

**응답** — `200 OK`

```json
{
  "accessToken": "eyJhbGciOiJIUzI1NiJ9..."
}
```

**잘못된 요청에 대한 응답**

| 상황 | 응답 |
| --- | --- |
| `email` 또는 `password` 가 없거나 공백뿐임 | 400 |
| 가입하지 않은 이메일 | 401 |
| 비밀번호가 틀림 | 401 |

<a id="logout"></a>
### 로그아웃과 토큰 무효화
로그아웃을 위한 엔드포인트를 새롭게 만듭니다.

`POST /auth/logout` — 요청에 담긴 Access Token 을 무효화합니다.

JWT 는 서명과 `exp` 만으로 검증되므로, 클라이언트가 토큰을 버리는 것만으로는 서버에서 그 토큰이 무효가 되지 않습니다. 누군가 그 토큰을 가지고 있다면 만료될 때까지 계속 쓸 수 있습니다. 그래서 로그아웃한 토큰을 서버가 기억해 두었다가, 이후 그 토큰으로 오는 요청을 거절해야 합니다.

**요청** — 별도 body 없음. 무효화할 토큰을 `Authorization` 헤더에 담아 보냅니다.

```
POST /auth/logout
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
```

**응답** — `204 No Content`

- 로그인한 사용자라면 가입 상태와 관계없이 누구나 호출할 수 있습니다.
- **요청에 쓴 그 토큰만** 무효화합니다. 같은 사용자가 다른 곳에서 로그인해 받은 토큰은 그대로 쓸 수 있습니다.
- 무효화된 토큰으로 로그인이 필요한 엔드포인트를 호출하면 401 입니다. ([토큰 검증](#토큰-검증--401)) 같은 토큰으로 다시 로그아웃해도 401 입니다.
- 무효화된 토큰은 서버가 재시작되어도 계속 무효여야 하므로 **DB 에 저장**합니다. 이를 위한 **새 테이블을 두는 것을 권장**합니다. 토큰 원문을 통째로 저장하기보다, 토큰을 발급할 때 고유한 ID(`jti` 클레임, 예: UUID)를 넣어 두고 그 값을 저장하는 것을 권장합니다.


### 토큰 검증 — 401

로그인이 필요한 엔드포인트를 호출할 때는 로그인으로 받은 `accessToken` 을 `Authorization` 헤더에 담아 보냅니다.

```
POST /seminars/1/enrollments
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...
```

서버는 요청마다 토큰을 검증해 요청자를 확인합니다. 아래 케이스들의 경우 인증에 실패한 것으로 간주하여 401을 응답합니다.

| 상황 | 응답 |
| --- | --- |
| `Authorization` 헤더가 없음 | 401 |
| `Bearer ` 로 시작하지 않음 | 401 |
| 토큰 형식이 올바르지 않음 | 401 |
| 서명이 올바르지 않음 (위조되었거나 다른 키로 서명됨) | 401 |
| 만료된 토큰 | 401 |
| 로그아웃으로 무효화된 토큰 | 401 |

- **위 규칙은 로그인이 필요한 모든 엔드포인트에 공통으로 적용되어야 합니다.**
- 인증 실패는 다른 어떤 검사보다 먼저 판단합니다. 예를 들어 요청 본문이 잘못되었거나 없는 리소스를 가리키더라도, 토큰이 유효하지 않으면 401 입니다.


401 과 403 도 2주차의 `ApiErrorResponse` 형식으로 응답하면 됩니다. 테스트 시에는 status code만 확인합니다.

## 2. 인가와 새 엔드포인트 구현

인가(Authorization)는 누구인지 확인된 사용자가 이 기능을 써도 되는지 판단하는 것입니다. 권한이 없으면(e.g. 역할, 가입 상태, 담당 세미나 등이 맞지 않음) `403` 을 반환합니다!

### 개요

이번 주에는 2주차에 구현한 엔드포인트 11개에 더해 **새 엔드포인트 7개**를 구현합니다. ([로그인](#login)과 [로그아웃](#logout)은 위 1장에서 설명했습니다.)

2주차 엔드포인트는 두 엔드포인트를 제외하고는 모두 요청과 응답을 그대로 두고 **인가 처리만 붙이면** 됩니다.

- [수강 신청](#enroll): 요청 본문의 `rookieId` 를 삭제합니다.
- [수강 취소](#enroll-cancel): 경로를 `/seminars/{seminarId}/enrollments/me` 로 바꿉니다.

요청자를 요청 본문이 아니라 토큰에서 확인하게 되었기 때문입니다...

### 역할과 가입 상태

| 역할 | 설명 |
| --- | --- |
| 와장 (`ADMIN`) | 서비스 전체를 관리합니다. 처음부터 DB에 존재합니다. |
| 운영진 (`STAFF`) | 세미나 하나를 담당하며 그 세미나를 운영합니다. |
| 루키 (`ROOKIE`) | 세미나를 수강합니다. |

- 와장은 모든 엔드포인트에 접근할 수 있습니다. (와장의 대쉬보드에 모든 기능이 보이는 것은 아니지만 권한은 모두 열어놓겠습니다. 와장의 권한은 주요 엔드포인트 몇 개에서 권한 실패가 일어나지 않는지만 간단히 테스트할 것입니다.)
- 운영진과 루키는 가입이 **승인(`APPROVED`)된 경우에만** 상응하는 권한을 가집니다.
- 가입 상태가 `PENDING` 이나 `REJECTED` 인 사용자는 공개 엔드포인트([가입 신청](#signup), [로그인](#login), [세미나 목록](#seminar-list))와 [로그아웃](#logout), [내 정보 조회](#me) 외에는 사용할 수 없습니다. **이 또한 403을 반환합니다.**

<a id="pagination"></a>
### 페이지네이션

세미나나 가입 신청처럼 개수가 계속 늘어나는 목록은 한 번에 모두 돌려주지 않고 일정한 개수씩 나눠서 돌려줍니다. 이를 **페이지네이션(pagination)** 이라 합니다. 목록이 수천 건이 되면 한 번에 응답하는 것은 DB, 서버, 네트워크 모두에 부담이 됩니다. 화면도 어차피 한 번에 일부만 보여 줍니다.

이번 주에는 다음 세 엔드포인트가 페이지 단위로 응답합니다.

- [내 수강 목록](#my-enrollments) `GET /users/me/enrollments`
- [가입 신청 목록](#user-list) `GET /users`
- [세미나 목록](#seminar-list) `GET /seminars`

#### `page` 와 `size`

클라이언트는 몇 번째 페이지(`page`)를 몇 개씩(`size`) 볼지 쿼리 파라미터로 보냅니다. `page` 는 **0부터** 셉니다.

예를 들어 항목이 45개이고 `size=20` 이면 다음과 같습니다.

| `page` | 받는 항목 | `content` 개수 |
| --- | --- | --- |
| 0 | 1 ~ 20번째 | 20 |
| 1 | 21 ~ 40번째 | 20 |
| 2 | 41 ~ 45번째 | 5 |

앞에서 건너뛸 항목 수(offset)는 `page × size` 입니다. SQL 로는 `LIMIT` 과 `OFFSET` 에 해당합니다.

```sql
-- 가입 신청 목록, page=2, size=20
SELECT * FROM users
WHERE ...
ORDER BY created_at DESC, id DESC
LIMIT 20 OFFSET 40;
```

#### 전체 개수와 전체 페이지 수

클라이언트가 "전체 3페이지 중 1페이지" 같은 화면을 그리려면 전체 항목 수도 알아야 합니다. 그래서 같은 조건으로 `COUNT` 쿼리를 한 번 더 실행해 `totalElements` 를 구합니다. `totalPages` 는 `totalElements ÷ size` 를 올림한 값입니다.

```sql
SELECT COUNT(*) FROM users WHERE ...;
```

위 예시에서 `page=2` 를 요청하면 응답은 다음과 같습니다.

```json
{
  "content": [ "... 5개 ..." ],
  "page": 2,
  "size": 20,
  "totalElements": 45,
  "totalPages": 3
}
```

#### 정렬 순서는 하나로 정해져야 합니다

`LIMIT`/`OFFSET` 은 정렬된 결과를 잘라 내는 것이므로, 요청할 때마다 정렬 순서가 같아야 합니다. `created_at` 처럼 같은 값이 여러 개 있을 수 있는 기준만으로 정렬하면, 같은 값끼리의 순서는 DB 가 정합니다. 그러면 페이지를 넘길 때 어떤 항목은 두 번 나오고 어떤 항목은 빠질 수 있습니다. 각 엔드포인트에 "일시가 같으면 ID 내림차순" 처럼 두 번째 기준을 적어 둔 이유입니다.

#### Spring 에서 구현할 때

- Spring Data JDBC 의 Repository 메서드는 `Pageable`(예: `PageRequest.of(page, size, sort)`)을 받아 `Page<T>` 를 돌려줄 수 있습니다. `@Query` 로 쿼리를 직접 쓴다면 `LIMIT`/`OFFSET` 쿼리와 `COUNT` 쿼리를 직접 작성하면 됩니다.
- 응답은 위 형식에 맞는 DTO 를 직접 만들어 돌려주세요. Spring 의 `Page` 를 그대로 반환하면 필드 이름과 구조가 이 명세와 다릅니다. 예를 들어 페이지 번호가 `page` 가 아니라 `number` 로 나갑니다.

> 더 알아보기: 이 방식(offset 기반)은 뒤쪽 페이지로 갈수록 DB 가 건너뛸 행이 많아져 느려집니다. 그래서 무한 스크롤처럼 데이터가 많은 화면에서는 "마지막으로 본 항목 다음부터" 가져오는 커서(cursor) 기반 방식도 많이 씁니다. 이번 과제에서는 offset 방식만 구현합니다.

## 3. 엔드포인트

- 각 엔드포인트에 적힌 403 경우는 모두 테스트로 확인합니다. 
- 2주차 엔드포인트의 요청, 응답, 기존 상태 코드는 2주차와 같습니다.


### 2주차 엔드포인트

<a id="signup"></a>
#### `POST /auth/signup`

로그인 없이 호출할 수 있습니다. 비밀번호를 원문이 아닌 Hash 로 저장하도록 바꿉니다.

<a id="user-get"></a>
#### `GET /users/{userId}`

가입이 승인된 사용자라면 역할과 관계없이 누구의 정보든 조회할 수 있습니다. 가입이 승인되지 않은(`PENDING`·`REJECTED`) 사용자가 요청하면 403 을 반환해야 합니다. 자기 자신의 정보를 조회하는 경우도 마찬가지이며, 이 사용자들은 [`GET /users/me`](#me) 를 사용합니다.

<a id="user-approval"></a>
#### `PATCH /users/{userId}/approval`

운영진의 가입 신청은 와장만 심사할 수 있습니다. 루키의 가입 신청은 와장과 운영진이 심사할 수 있습니다. 운영진이 운영진의 가입 신청을 심사하려 하면 403 을 반환해야 합니다. 루키가 요청하면 403 입니다. 가입이 승인되지 않은 운영진이 요청해도 403 입니다.

<a id="seminar-create"></a>
#### `POST /seminars`

와장만 세미나를 개설할 수 있습니다. 운영진 또는 루키가 요청하면 403입ㄴ다.

<a id="seminar-get"></a>
#### `GET /seminars/{seminarId}`

가입이 승인된 사용자라면 역할과 관계없이 조회할 수 있습니다. 가입이 승인되지 않은(`PENDING`·`REJECTED`) 사용자가 요청하면 403 을 반환해야 합니다.

<a id="seminar-update"></a>
#### `PATCH /seminars/{seminarId}`

와장과, 해당 세미나를 담당하는 운영진이 수정할 수 있습니다. 다른 세미나를 담당하는 운영진 또는 루키가 요청하면 403 을 반환해야 합니다.

<a id="session-create"></a>
#### `POST /seminars/{seminarId}/sessions`

와장과, 해당 세미나를 담당하는 운영진이 회차를 등록할 수 있습니다. 다른 세미나를 담당하는 운영진이 요청하면 403 을 반환해야 합니다. 루키가 요청해도 403 입니다. 담당 운영진이라도 가입이 승인되지 않은 상태라면 403 입니다.

<a id="session-list"></a>
#### `GET /seminars/{seminarId}/sessions`

와장, 해당 세미나를 담당하는 운영진, 해당 세미나를 수강 중인 루키가 조회할 수 있습니다. 그 세미나를 신청하지 않은 루키가 요청하면 403 을 반환해야 합니다. 다른 세미나를 담당하는 운영진이 요청해도 403 입니다. 가입이 승인되지 않은 사용자가 요청해도 403 입니다.

<a id="session-get"></a>
#### `GET /sessions/{sessionId}`

[회차 목록](#session-list) 과 같습니다. 와장, 회차가 속한 세미나를 담당하는 운영진, 그 세미나를 수강 중인 루키가 조회할 수 있습니다. 그 세미나를 신청하지 않은 루키가 요청하면 403 을 반환해야 합니다. 다른 세미나를 담당하는 운영진이 요청해도 403 입니다.

<a id="enroll"></a>
#### `POST /seminars/{seminarId}/enrollments`

**3주차 변경** — 요청 본문의 `rookieId` 를 삭제합니다. 토큰을 통해 요청자를 식별합니다.

가입이 승인된 루키만 신청할 수 있습니다. 운영진이 요청하면 403 을 반환해야 합니다. 가입이 승인되지 않은(`PENDING`·`REJECTED`) 루키가 요청해도 403 입니다.

2주차에는 루키가 아닌 사용자의 신청에 400 을 반환했지만, 3주차부터는 권한 표에 맞춰 403 을 반환합니다.

** 2주차의 "`rookieId` 가 없는 리소스를 가리킴(404)" 은 없어집니다.

<a id="enroll-cancel"></a>
#### `DELETE /seminars/{seminarId}/enrollments/me`

**3주차 변경** — 경로가 `/seminars/{seminarId}/enrollments/{enrollmentId}` 에서 `/seminars/{seminarId}/enrollments/me` 로 바뀝니다. 토큰의 주인이 이 세미나에 낸 신청을 취소합니다.

가입이 승인된 루키가 자신의 신청만 취소할 수 있습니다. 운영진이 요청하면 403 을 반환해야 합니다. 




### 새 엔드포인트

<a id="me"></a>
#### `GET /users/me`

로그인한 사용자 자신의 정보를 조회합니다.로그인을 통해 토큰을 발급받은 사용자라면 누구나 이용할 수 있습니다.

**요청** — 별도 body 없음.

**응답** — `200 OK`

2주차의 `GET /users/{userId}` 와 같은 형식입니다.

```json
{
  "id": 1,
  "email": "waffle@snu.ac.kr",
  "name": "김와플",
  "githubUsername": "waffle-kim",
  "role": "ROOKIE",
  "status": "PENDING",
  "seminarId": null,
  "createdAt": "2026-09-15T21:02:00+09:00"
}
```

<a id="my-enrollments"></a>
#### `GET /users/me/enrollments`

루키가 자신이 신청한 세미나 목록을 조회합니다.

가입이 승인된 루키만 호출할 수 있습니다. 운영진이 요청하면 403 을 반환해야 합니다. 가입이 승인되지 않은(`PENDING`·`REJECTED`) 루키가 요청해도 403 입니다.

**요청** — 쿼리 파라미터

| 항목 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `page` | integer | | 0부터 시작하는 페이지 번호. 기본값 0 |
| `size` | integer | | 한 페이지의 크기. 기본값 20, 최대 100 |

**응답** — `200 OK`

목록은 페이지 단위로 응답합니다.

```json
{
  "content": [
    {
      "id": 10,
      "seminar": {
        "id": 1,
        "title": "Spring 세미나",
        "description": "…",
        "status": "OPEN",
        "capacity": 30,
        "enrolledCount": 12,
        "applyStartAt": "2026-09-14T10:00:00+09:00",
        "applyEndAt": "2026-09-21T23:59:00+09:00"
      },
      "graceDaysRemaining": 3,
      "dropped": false,
      "createdAt": "2026-09-15T21:02:00+09:00"
    }
  ],
  "page": 0,
  "size": 20,
  "totalElements": 1,
  "totalPages": 1
}
```

| 항목 | 타입 | 설명 |
| --- | --- | --- |
| `content` | array | 이 페이지의 항목들 |
| `page`, `size` | integer | 요청한 페이지 번호와 크기 |
| `totalElements` | integer | 전체 항목 수 |
| `totalPages` | integer | 전체 페이지 수. 항목이 없으면 0 |

- `content` 의 `id` 는 수강 신청(enrollment)의 ID 입니다.
- `seminar` 의 각 항목은 `GET /seminars/{seminarId}` 의 같은 이름 항목과 같은 의미입니다.
- 최근에 신청한 순서로 정렬합니다. 신청 일시가 같으면 ID 내림차순입니다.


<a id="user-list"></a>
#### `GET /users`

가입 신청 목록을 조회합니다. 와장과 운영진이 가입 심사 화면에서 사용합니다.

와장과 운영진만 조회할 수 있습니다. 와장은 운영진과 루키의 신청을 모두 보고, 운영진은 루키의 신청만 봅니다. 운영진이 `role=STAFF` 로 요청해도 루키의 신청만 돌려줘야 합니다. 루키가 요청하면 403 을 반환해야 합니다. 가입이 승인되지 않은 운영진이 요청해도 403 입니다.

**요청** — 쿼리 파라미터

| 항목 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `status` | string | | `PENDING`, `APPROVED`, `REJECTED` 중 하나. 없으면 전체 |
| `role` | string | | `STAFF`, `ROOKIE` 중 하나. 없으면 전체. 운영진이 보내면 무시합니다 |
| `page`, `size` | integer | | [내 수강 목록](#my-enrollments) 과 같습니다 |

**응답** — `200 OK`

목록 응답의 형식은 [내 수강 목록](#my-enrollments) 과 같습니다. `content` 의 각 항목은 `GET /users/{userId}` 와 같은 형식입니다.

- 와장 계정은 목록에 나오지 않습니다.
- 최근에 가입한 순서로 정렬합니다. 가입 일시가 같으면 ID 내림차순입니다.

**잘못된 요청에 대한 응답**

| 상황 | 응답 |
| --- | --- |
| `status` 나 `role` 이 정해진 값이 아님 | 400 |

<a id="seminar-list"></a>
#### `GET /seminars`

세미나 목록을 조회하고 제목으로 검색합니다.

로그인 없이 호출할 수 있습니다. 운영진으로 가입하려는 사용자가, 계정이 만들어지기 전에 담당할 세미나를 골라야 하기 때문입니다.

**요청** — 쿼리 파라미터

| 항목 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `keyword` | string | | 제목에 이 문자열이 포함된 세미나만. 없거나 공백뿐이면 전체 |
| `status` | string | | `BEFORE`, `OPEN`, `CLOSED` 중 하나. 없으면 전체 |
| `page`, `size` | integer | | [내 수강 목록](#my-enrollments) 과 같습니다 |

**응답** — `200 OK`

목록 응답의 형식은 [내 수강 목록](#my-enrollments) 과 같습니다. `content` 의 각 항목은 `GET /seminars/{seminarId}` 와 같은 형식입니다.

- 세미나 ID 오름차순으로 정렬합니다.
- `status` 는 단건 조회와 같은 규칙으로 계산한 값입니다.

**잘못된 요청에 대한 응답**

| 상황 | 응답 |
| --- | --- |
| `status` 가 정해진 값이 아님 | 400 |

<a id="session-update"></a>
#### `PATCH /sessions/{sessionId}`

회차의 정보와 수업·과제 설명을 고칩니다.

와장과, 회차가 속한 세미나를 담당하는 운영진이 수정할 수 있습니다. 다른 세미나를 담당하는 운영진이 요청하면 403 을 반환해야 합니다. 루키가 요청해도 403 입니다. 담당 운영진이라도 가입이 승인되지 않은 상태라면 403 입니다.

**요청**

```json
{
  "title": "Database, ERD, Swagger",
  "lectureContent": null
}
```

| 항목 | 타입 | 필수 | 제약 |
| --- | --- | --- | --- |
| `title` | string | | 공백 불가 |
| `startsAt` | string | | ISO-8601 일시 |
| `location` | string | | 공백 불가 |
| `assignmentTitle` | string | | 공백 불가 |
| `lectureContent` | string \| null | | Markdown. `null`을 보내면 설명을 지웁니다 |
| `assignmentContent` | string \| null | | Markdown. `null`을 보내면 설명을 지웁니다 |

- 보낸 항목만 고칩니다. 보내지 않은 항목은 그대로 둡니다.
- `lectureContent`, `assignmentContent` 는 키를 보내지 않은 것과 `null` 을 보낸 것이 서로 다른 요청입니다. 2주차의 `PATCH /seminars/{seminarId}` 의 `description` 과 같습니다.
- `startsAt` 을 바꾸면 이 세미나의 회차 번호(`round`)가 다시 매겨질 수 있습니다.

**응답** — `200 OK`

`GET /sessions/{sessionId}` 와 같은 형식으로, 수정된 회차를 응답합니다.

**잘못된 요청에 대한 응답**

| 상황 | 응답 |
| --- | --- |
| `title`, `location`, `assignmentTitle` 이 공백뿐 | 400 |
| 없는 회차 | 404 |
