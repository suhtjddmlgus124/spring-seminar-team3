### 개발 환경 설정 파일들

**`compose.yaml`** — 개발용 MySQL 8.4 를 띄웁니다. 각자 컴퓨터에 MySQL 을 설치하지 않고
도커로 띄우는 이유는 조원 모두 같은 종류와 버전을 쓰기 위해서입니다.

| | 값 |
| --- | --- |
| 포트 | `3306` |
| 데이터베이스 · 계정 · 비밀번호 | 모두 `waggle` |

```bash
docker compose up -d      # 띄우기
docker compose down       # 내리기 (데이터는 볼륨에 남습니다)
docker compose down -v    # 데이터까지 지우기
```

**`src/main/resources/application.yaml`** — 애플리케이션 설정입니다. 두 가지가 들어 있습니다.

- `spring.datasource` : 위 MySQL 에 어떻게 접속할지. compose.yaml 의 값과 맞춰 두었습니다.
- `spring.flyway.locations` : 마이그레이션 파일을 어디서 찾을지. `db/migration` 입니다.

애플리케이션이 뜰 때 Flyway 가 이 경로의 `V{n}__*.sql` 을 버전 순서대로 실행합니다.

### 의존성과 관련하여

`build.gradle.kts`에 이번 주차에 필요한 의존성을 넣어 두었습니다.

| 의존성 | 하는 일 |
| --- | --- |
| `spring-boot-starter-webmvc` | HTTP 요청을 받는 웹 계층. 1주차부터 쓰던 것 |
| `spring-boot-starter-validation` | `@NotBlank`, `@Min` 같은 요청 값 검증 |
| `spring-boot-starter-data-jdbc` | **Spring Data JDBC.** 테이블과 객체를 잇고 Repository를 만들어 줍니다 |
| `mysql-connector-j` | MySQL JDBC 드라이버 |
| `spring-boot-starter-flyway`, `flyway-mysql` | 마이그레이션을 순서대로 실행 |
| `springdoc-openapi-starter-webmvc-ui` | 코드에서 OpenAPI 문서와 Swagger UI 생성 |
| `testcontainers:mysql` | 테스트할 때 MySQL 컨테이너를 띄우고 지움 |


채점 서버는 `build.gradle.kts` 를 과제 원본의 것으로 바꿔서 돌립니다. 의존성을 더하면
로컬에서는 되지만 채점에서는 없는 것이 되어 컴파일부터 실패합니다.
필요한 의존성이 있으면 운영진에게 알려주세요.

## 2. ERD 설계

코드를 쓰기 전에, 조원이 모여 요구사항을 함께 파악하여 테이블 스킴을 정하세요.

ERD는 2주차 과제와 무관하게 **서비스 요구사항 전체**를 고려해서 설계하는 것이 좋습니다. 2주차 구현 범위만 고려해서 설계하게 되면, 이후 DB 마이그레이션을 여러번 거쳐야 하기 때문...

다만 2주차 테스트는 [기능 개발](#3-기능-개발)의 범위만을 고려합니다.

### 설계한 것을 DDL 로 옮기기

설계가 끝나면 `CREATE TABLE` 문을 **`src/main/resources/db/migration/V1__init.sql`** 에
작성합니다. 받은 파일은 주석만 있는 빈 파일입니다.

애플리케이션이 뜰 때 Flyway 가 이 파일을 실행해 테이블을 만듭니다. 테스트도 마찬가지라,
이 파일이 비어 있으면 테이블이 없어 아무것도 동작하지 않습니다.


**테이블 설계 자체는 채점 대상이 아닙니다.** 코드에 대한 채점은 공개 테스트 통과 여부로만 합니다.

## 3. 기능 개발
[waggle](https://waggle.wafflestudio.com) 을 위한 엔드포인트 중 일부를 이번 2주차 과제로 구현합니다. 아래 엔드포인트를 팀원끼리 나누어 구현합니다.

### 에러 응답

1주차에 만든 형식을 그대로 씁니다. 스켈레톤의 `ApiErrorResponse`와 `GlobalExceptionHandler`가 이미 이렇게 내보냅니다.

```json
{
  "code": "SEMINAR_NOT_FOUND",
  "message": "ID가 999인 세미나를 찾을 수 없습니다.",
  "fieldErrors": []
}
```

```json
{
  "code": "INVALID_REQUEST",
  "message": "요청값이 올바르지 않습니다.",
  "fieldErrors": [
    { "field": "capacity", "message": "정원은 1명 이상이어야 합니다." }
  ]
}
```

`code`와 `message`에 무엇을 담을지는 팀이 정합니다. 테스트는 **상태 코드만** 확인합니다. 어떤 상황에 어떤 상태 코드를 내보내야 하는지는 엔드포인트마다 표로 적어 두었습니다.

### 2주차 인증·인가 범위

2주차에는 호출자를 식별하는 인증과, 호출자가 해당 기능을 실행할 권한이 있는지 확인하는 인가를 **구현하거나 검증하지 않습니다.** 따라서 이 문서의 요청에는 로그인 사용자 정보가 없으며, 세미나 개설자의 `ADMIN` 여부, 회차 등록자가 담당 `STAFF`인지 여부, 수강 신청의 `rookieId`가 호출자 본인인지 여부는 3주차에 구현합니다.

다만 가입 심사 상태는 인증·인가와 별개의 서비스 규칙입니다. 수강 신청은 `APPROVED` 상태의 `ROOKIE`만 할 수 있습니다. 2주차에는 가입 심사 상태를 전환하는 API를 구현합니다. 이 API를 누가 호출할 수 있는지는 3주차에 인증·인가를 붙여 제한합니다.

### 구현할 엔드포인트

| 기능 | 메서드와 경로 |
| --- | --- |
| 가입 신청 | `POST /auth/signup` |
| 사용자 단건 조회 | `GET /users/{userId}` |
| 가입 심사 | `PATCH /users/{userId}/approval` |
| 세미나 개설 | `POST /seminars` |
| 세미나 단건 조회 | `GET /seminars/{seminarId}` |
| 세미나 수정 | `PATCH /seminars/{seminarId}` |
| 회차 등록 | `POST /seminars/{seminarId}/sessions` |
| 회차 목록 | `GET /seminars/{seminarId}/sessions` |
| 회차 단건 조회 | `GET /sessions/{sessionId}` |
| 수강 신청 | `POST /seminars/{seminarId}/enrollments` |
| 수강 취소 | `DELETE /seminars/{seminarId}/enrollments/{enrollmentId}` |

팀원 별 구현의 책임은 계층이 아니라 기능 단위로 나누세요. e.g. 가입·사용자 / 세미나 / 회차 / 수강 신청 정도


### 가입과 사용자

#### `POST /auth/signup`

`ROOKIE` 또는 `STAFF` 으로 가입을 신청합니다. role 필드에서 어떤 역할로 가입할지 명시합니다. `STAFF` 인 경우 본인이 맡을 세미나의 seminar_id를 함께 명시합니다. `ADMIN`은 가입으로 생성되지 않고 DB에 미리 존재하는 역할이므로, `ADMIN`으로 가입을 요청하면 잘못된 요청입니다.

**요청**

```json
{
  "email": "waffle@snu.ac.kr",
  "password": "********",
  "name": "김와플",
  "githubUsername": "waffle-kim",
  "role": "ROOKIE",
  "seminarId": null
}
```

| 항목 | 타입 | 필수 | 제약 |
| --- | --- | --- | --- |
| `email` | string | ✓ | 이메일 형식 |
| `password` | string | ✓ | 공백 불가 |
| `name` | string | ✓ | 공백 불가 |
| `githubUsername` | string | ✓ | 공백 불가 |
| `role` | string | ✓ | `STAFF` 또는 `ROOKIE` |
| `seminarId` | integer \| null | 운영진만 | 운영진이면 필수, 루키면 `null`이거나 생략 |

**응답** — `201 Created`

```json
{
  "id": 1,
  "status": "PENDING",
  "createdAt": "2026-09-15T21:02:00+09:00"
}
```

`id`는 integer이고, `createdAt`은 ISO 8601 형식, `status`는 "PENDING" 고정입니다.


**잘못된 요청에 대한 응답**

| 상황 | 응답 |
| --- | --- |
| `email`이 이메일 형식이 아님 | 400 |
| `password`, `name`, `githubUsername` 중 하나가 공백이거나 비어 있음 | 400 |
| `role`이 `ROOKIE`, `STAFF` 외의 값임 | 400 |
| `STAFF` 가입 요청에 `seminarId`가 없거나, `ROOKIE` 가입 요청에 null이 아닌 `seminarId`가 있음 | 400 |
| `seminarId`가 없는 세미나를 가리킴 | 404 |
| 이미 가입한 이메일 | 409 |

#### `GET /users/{userId}`

사용자 한 명을 조회합니다.

**요청**

별도 body 없음.

**응답** — `200 OK`

```json
{
  "id": 1,
  "email": "waffle@snu.ac.kr",
  "name": "김와플",
  "githubUsername": "waffle-kim",
  "role": "STAFF",
  "status": "PENDING",
  "seminarId": 3,
  "createdAt": "2026-09-15T21:02:00+09:00"
}
```

인자로 준 userId에 해당하는 유저의 정보가 조회되어야 합니다.

**잘못된 요청에 대한 응답**

| 상황 | 응답 |
| --- | --- |
| 없는 사용자 | 404 |

#### `PATCH /users/{userId}/approval`

대기 중인 가입 신청을 승인하거나 반려합니다. 2주차에는 호출자의 권한을 확인하지 않습니다.

**요청**

```json
{ "status": "APPROVED" }
```

| 항목 | 타입 | 필수 | 제약 |
| --- | --- | --- | --- |
| `status` | string | ✓ | `APPROVED` 또는 `REJECTED` |

**응답** — `200 OK`

`GET /users/{userId}`와 같은 형식으로, 전환된 `status`를 포함해 응답합니다.

**규칙**

- `PENDING` 상태의 사용자만 `APPROVED` 또는 `REJECTED`로 전환할 수 있습니다.
- 이미 `APPROVED` 또는 `REJECTED`인 사용자의 상태는 다시 바꿀 수 없습니다.

**잘못된 요청에 대한 응답**

| 상황 | 응답 |
| --- | --- |
| `status`가 없거나 `APPROVED`, `REJECTED` 외의 값임 | 400 |
| 없는 사용자 | 404 |
| 사용자의 상태가 `PENDING`이 아님 | 409 |



### 세미나

#### `POST /seminars`

세미나를 개설합니다.

**요청**

```json
{
  "title": "Spring 세미나",
  "description": "## 세미나 소개\n\n…",
  "capacity": 30,
  "applyStartAt": "2026-09-14T10:00:00+09:00",
  "applyEndAt": "2026-09-21T23:59:00+09:00",
  "totalGraceDays": 3
}
```

| 항목 | 타입 | 필수 | 제약 |
| --- | --- | --- | --- |
| `title` | string | ✓ | 공백 불가 |
| `description` | string \| null | | Markdown |
| `capacity` | integer | ✓ | 1 이상 |
| `applyStartAt` | string | ✓ | ISO-8601 일시. |
| `applyEndAt` | string | ✓ | ISO-8601 일시. `applyStartAt`보다 뒤 |
| `totalGraceDays` | integer | ✓ | 0 이상 |

**응답** — `201 Created`

```json
{
  "id": 1,
  "createdAt": "2026-09-15T21:02:00+09:00"
}
```

`id`는 integer, `createdAt`은 ISO 8601 형식입니다. 나머지 정보는 단건 조회에서 받습니다.

**잘못된 요청에 대한 응답**

| 상황 | 응답 |
| --- | --- |
| `title`이 비어 있거나 공백뿐임 | 400 |
| `capacity`가 1 미만임 | 400 |
| `applyEndAt`이 `applyStartAt`보다 뒤가 아님 | 400 |
| `totalGraceDays`가 0 미만임 | 400 |

#### `GET /seminars/{seminarId}`

세미나 하나를 조회합니다. 현재 신청 인원(enrolledCount)과 신청 상태(status)가 함께 나옵니다.

**응답** — `200 OK`

```json
{
  "id": 1,
  "title": "Spring 세미나",
  "description": "…",
  "capacity": 30,
  "enrolledCount": 0,
  "applyStartAt": "2026-09-14T10:00:00+09:00",
  "applyEndAt": "2026-09-21T23:59:00+09:00",
  "totalGraceDays": 3,
  "status": "CLOSED",
  "sessionCount": 2
}
```

| 항목 | 타입 | 설명 |
| --- | --- | --- |
| `id`, `capacity`, `totalGraceDays` | integer | 개설할 때 정한 값 |
| `title` | string | |
| `description` | string \| null | Markdown |
| `applyStartAt`, `applyEndAt` | string | ISO-8601 일시 |
| `enrolledCount` | integer | 현재 신청 인원 |
| `sessionCount` | integer | 등록된 회차 수 |
| `status` | string | 신청 상태 |

**규칙**

- `enrolledCount`는 이 세미나를 지금 신청한 인원 수입니다. 정원 `capacity` 에 도달하면 신청 기간 안이라 하더라도 어도 `status`가 `CLOSED`가 됩니다.
- `status`는 이 세미나의 신청 상태를 말합니다. status의 응답 조건은 다음과 같습니다.

| `status` | 조건 |
| --- | --- |
| `BEFORE` | 현재 < 신청 시작 일시(단, 아직 신청인원이 정원에 도달하지 않음) |
| `CLOSED` | 신청 종료 일시 ≤ 현재 **또는** 신청 인원이 정원에 도달 |
| `OPEN` | 나머지 |


**잘못된 요청에 대한 응답**

| 상황 | 응답 |
| --- | --- |
| 없는 세미나 | 404 |

#### `PATCH /seminars/{seminarId}`

세미나의 제목 또는 설명을 고칩니다.

**요청**

```json
{ "title": "Spring Boot 세미나" }
```

| 항목 | 타입 | 필수 | 제약 |
| --- | --- | --- | --- |
| `title` | string | | 공백 불가. `null` 불가 |
| `description` | string \| null | | Markdown. `null`을 보내면 설명을 지웁니다 |

**응답** — `200 OK`

```json
{
  "id": 1,
  "title": "Spring Boot 세미나",
  "description": "…",
  "capacity": 30,
  "enrolledCount": 12,
  "applyStartAt": "2026-09-14T10:00:00+09:00",
  "applyEndAt": "2026-09-21T23:59:00+09:00",
  "totalGraceDays": 3,
  "status": "OPEN",
  "sessionCount": 0
}
```

- 세미나를 단건 조회 하는 경우와 응답형식이 같습니다. 
- title 만, 또는 description만, 또는 title과 description을 동시에 수정하는 것이 가능합니다.
- `title`, `description` 외의 필드는 무시합니다.

**잘못된 요청에 대한 응답**

| 상황 | 응답 |
| --- | --- |
| `title`의 value가 null이거나 공백뿐 | 400 |
| 없는 세미나 | 404 |


### 수업 회차

#### `POST /seminars/{seminarId}/sessions`

세미나에 수업 회차를 하나 등록합니다. 수업 회차를 만들때에 그 회차에 딸린 과제를 함께 만드는 형태입니다.

**요청**

```json
{
  "title": "Database, ERD, Swagger",
  "startsAt": "2026-09-22T19:00:00+09:00",
  "location": "302동 208호",
  "assignmentTitle": "ERD 설계",
  "lectureContent": "## 수업\n\n…",
  "assignmentContent": "## 과제\n\n…"
}
```

| 항목 | 타입 | 필수 | 제약 |
| --- | --- | --- | --- |
| `title` | string | ✓ | 공백 불가 |
| `startsAt` | string | ✓ | ISO-8601 일시 |
| `location` | string | ✓ | 공백 불가 |
| `assignmentTitle` | string | ✓ | 공백 불가 |
| `lectureContent` | string \| null | | Markdown |
| `assignmentContent` | string \| null | | Markdown |

**응답** — `201 Created`

```json
{
  "id": 7,
  "seminarId": 1,
  "round": 1
}
```

- 셋 다 integer입니다.
- `round`는 저장하는 값이 아니라, 해당 세미나의 회차를 `startsAt` 오름차순으로 정렬했을 때의 순서입니다. `startsAt`이 같으면 회차 ID 오름차순으로 정렬합니다.
- 회차는 날짜 순서와 관계없이 등록할 수 있습니다. 더 이른 `startsAt`의 회차를 나중에 등록하면 기존 회차의 `round`가 달라질 수 있습니다.
- 회차마다 과제가 항상 하나 있습니다. `assignmentTitle`이 필수인 이유입니다.

**잘못된 요청에 대한 응답**

| 상황 | 응답 |
| --- | --- |
| `title`, `startsAt`, `location`, `assignmentTitle` 중 하나가 없거나 공백뿐임 | 400 |
| 없는 세미나 | 404 |

#### `GET /seminars/{seminarId}/sessions`

세미나의 수업 회차들을 조회합니다.

**응답** — `200 OK`

```json
[
  {
    "id": 7,
    "seminarId": 1,
    "round": 1,
    "title": "Database, ERD, Swagger",
    "startsAt": "2026-09-22T19:00:00+09:00",
    "location": "302동 208호",
    "assignmentTitle": "ERD 설계"
  }
]
```

- `round` 오름차순으로 **배열**로 돌려줍니다. 
- **목록에는 설명 본문(`lectureContent`, `assignmentContent`)을 담지 않습니다.**
- 회차가 없으면 빈 배열입니다.

**잘못된 요청에 대한 응답**

| 상황 | 응답 |
| --- | --- |
| 없는 세미나 | 404 |

회차 하나를 **수업·과제 설명까지를 포함하여** 조회합니다.

**응답** — `200 OK`

```json
{

  "seminarId": 1,
  "round": 1,
  "title": "Database, ERD, Swagger",
```

회차 목록의 항목에 `lectureContent`와 `assignmentContent`가 더해진 형태입니다. 설명이 없으면 `null`입니다.

**잘못된 요청에 대한 응답**

| 상황 | 응답 |
| --- | --- |
| 없는 회차 | 404 |



### 수강 신청

#### `POST /seminars/{seminarId}/enrollments`

루키가 세미나를 신청합니다. 선착순이라 별도 승인 없이 즉시 확정됩니다.

**요청**

```json
{ "rookieId": 5 }
```

| 항목 | 타입 | 필수 | 제약 |
| --- | --- | --- | --- |
| `rookieId` | integer | ✓ | 역할이 `ROOKIE`이고 가입 상태가 `APPROVED`인 사용자 |

**응답** — `201 Created`

```json
{
  "id": 10,
  "graceDaysRemaining": 3,
  "createdAt": "2026-09-15T21:02:00+09:00"
}
```

- `graceDaysRemaining`은 세미나의 `totalGraceDays`에서 시작합니다.
- 세미나의 `status`가 `OPEN`이어야 합니다. 즉 신청 기간 안이고 정원이 남아 있어야 합니다.
- 한 루키가 같은 세미나를 두 번 신청할 수는 없습니다. 신청할 수 있는 세미나 개수에는 제한이 없습니다.



**잘못된 요청에 대한 응답**

| 상황 | 응답 |
| --- | --- |
| `rookieId`가 루키가 아님 | 400 |
| `rookieId`가 `PENDING` 또는 `REJECTED` 상태임 | 403 |
| `rookieId` 또는 `seminarId`가 없는 리소스를 가리킴 | 404 |
| 세미나가 `OPEN`이 아니거나 이미 신청함 | 409 |

#### `DELETE /seminars/{seminarId}/enrollments/{enrollmentId}`

루키의 수강 신청을 취소합니다.

**요청**

별도 body 없음.

**응답** — `204 No Content`

응답 body는 없습니다.

**규칙**

- 신청 시작 일시부터 신청 종료 일시 전까지 취소할 수 있습니다. 즉 `applyStartAt ≤ 현재 < applyEndAt`이어야 합니다.
- 세미나가 정원 도달로 `CLOSED`인 경우에도, 신청 기간 안이라면 취소할 수 있습니다.
- 취소하면 해당 enrollment 레코드를 삭제합니다. 따라서 `enrolledCount`가 하나 감소하고, 다른 루키가 빈자리에 신청할 수 있습니다.
- 2주차에는 인증·인가를 구현하지 않으므로 취소 요청자가 enrollment의 루키 본인인지는 검증하지 않습니다. 3주차에 로그인 사용자와 enrollment의 루키가 같은지 확인합니다.

**잘못된 요청에 대한 응답**

| 상황 | 응답 |
| --- | --- |
| 해당 세미나의 enrollment를 찾을 수 없음 | 404 |
| 신청 기간 전 또는 신청 종료 후 | 409 |

## 4. 코드 리뷰와 머지

PR은 팀원 **한 명 이상**의 review와 approve를 받은 뒤 `main`에 머지합니다. 특별한 경우가 아니라면 로컬에서 `main`으로 직접 push하지 않습니다❗❗

한 팀원이 여러 PR을 올리는 것은 괜찮습니다. 단 모든 팀원이 적어도 하나 이상의 커밋으로 기여해야 합니다.

## 5. 채점 확인

로컬에서는 이 명령으로 확인합니다.

```bash
./gradlew test
```

`main`에 push하면 GitHub Actions 가 같은 테스트를 채점 서버에서 돌립니다.
결과는 [리더보드](https://spring-seminar-judge.vercel.app/)에서 확인합니다.

채점 서버는 여러분의 저장소에서 **`src/main` 만** 가져가고, 테스트와 `build.gradle.kts` 는
과제 원본의 것을 씁니다. 그래서 두 가지를 기억해두세요.

- 테스트 코드를 고쳐도 채점 결과는 달라지지 않습니다.
- `src/main/resources` 는 가져가므로 팀이 작성한 `db/migration/V1__init.sql` 로 채점합니다.
